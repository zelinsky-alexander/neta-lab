# Large-Scale Simulator — Phase 3 Windows Fleet

Branch: `large-scale-simulator`

## Goal

Phase 3 adds the Windows half of the realistic fleet demo. One Windows Server host runs a host-wide NETA ETW sensor broker and many process-isolated Windows containers. Every logical endpoint keeps its own NETA identity, SQLite database, network context, persona and scenario history. Randomness chooses endpoint behavior; the lab never fabricates a NETA finding.

Target progression:

```text
10 -> 50 -> 100 -> 250 -> 500 Windows endpoints
```

Do not progress beyond ten until the Phase-3 acceptance harness passes.

## Architecture

```text
Windows Server host
    |
    +-- native ETW lifecycle/process collectors (one copy)
    |       |
    |       v
    |   neta-agent sensor-broker
    |       |
    |       +-- process-tree attribution: root PID -> endpoint slot
    |       +-- named-pipe client PID verification
    |       +-- bounded per-endpoint queues
    |       |
    |       +---- WIN-0001 broker-mode neta-agent.exe
    |       +---- WIN-0002 broker-mode neta-agent.exe
    |       +---- ...
    |
    +-- Docker/HNS process-isolated Windows containers
            +-- persistent supervisor process
            +-- real NETA agent process
            +-- Windows-native NETA-LAB processes
            +-- independent filesystem/registry/network/process namespace
```

The attribution key is not IP address. The orchestrator seeds the broker with the host-visible root PID of every endpoint container. Process starts inherit ownership from their parent process. Lifecycle events are routed through the same PID ownership registry. When a broker-mode agent connects, the named-pipe server obtains the real host client PID and rejects registration unless that PID belongs to the requested endpoint slot.

## Windows evidence boundary

Phase 3 brokers the host-wide evidence that would otherwise require one ETW session per endpoint:

- TCP connect/accept/close lifecycle events;
- process start/exit events;
- parent/child process identity;
- command line and executable path;
- Windows user/session/integrity/elevation fields supplied by the native collector.

The endpoint agent continues to use the normal production connection snapshot, route, evidence, rule, finding, SQLite and FleetClient/NAP paths from inside its container.

DNS Client ETW and Schannel ETW are explicitly reported unavailable in broker mode in this phase rather than starting hundreds of duplicate host-wide ETW sessions. Multiplexing those streams can be added later without changing the endpoint identity model. Unsupported evidence is never fabricated.

## Process isolation

Windows process-isolated containers share the Windows kernel, but Windows isolates their process/thread ID namespace, filesystem, registry and network namespace. NETA's host broker sees the host processes and maps them back to one endpoint through the container supervisor process tree.

Example:

```text
WIN-0001
  supervisor
    neta-agent.exe

WIN-0002
  supervisor
    neta-agent.exe
    powershell.exe
      windows-update-helper.exe
        whoami.exe
        hostname.exe
        ipconfig.exe

WIN-0003
  supervisor
    neta-agent.exe
    curl.exe -> controlled HTTP peer
```

The process events under `WIN-0002` are delivered only to `WIN-0002`; the network events generated by `WIN-0003` are delivered only to `WIN-0003`.

## Host requirements

Recommended host: Windows Server 2025 with Windows containers and a Windows Docker engine. Windows Server 2022 is also usable with a matching container image.

Required software:

- Windows Containers feature;
- Docker Engine configured for Windows containers;
- Python 3 for the NETA lab orchestrator;
- a Windows build of `neta-agent.exe` from the matching `large-scale-simulator` branch;
- process-isolated Windows container image compatible with the host build.

The default image is:

```text
mcr.microsoft.com/windows/servercore:ltsc2025
```

Override it in `fleet/config/windows-default.json` when the host uses another supported Windows Server release.

## Named-pipe bootstrap

Docker/HCS deliberately maps the host NETA broker pipe into every endpoint container. The orchestrator briefly creates a bootstrap named pipe while containers are created and started, obtains each host-visible container root PID, then replaces the bootstrap with the real NETA sensor broker using the complete endpoint map. Agents are started only after the real broker is ready.

The pipe is host-local and must never be exposed as a network protocol.

## Persistent state

Default state root:

```text
C:\ProgramData\NETA-Lab\fleet\windows-default\
  broker.log
  acceptance-phase3.json
  ground-truth\runs.jsonl
  endpoints\
    win-0001\
      endpoint.json
      persona.json
      identity\
      neta.db
      ground-truth.jsonl
      control\
      logs\
      scenarios\
```

Container lifecycle is disposable. Endpoint identity/database/persona state is host-mounted and survives a container recreation.

## Start ten endpoints

For sensor isolation work without coordinator enrollment:

```powershell
.\automation\neta-fleet-windows.ps1 `
  --agent ..\neta-agent\build-windows\Release\neta-agent.exe `
  --allow-unenrolled `
  up --count 10
```

For the full NAP/mTLS path supply one unused enrollment token per endpoint:

```powershell
.\automation\neta-fleet-windows.ps1 `
  --agent ..\neta-agent\build-windows\Release\neta-agent.exe `
  up --count 10 `
  --coordinator https://coordinator.example:8443 `
  --fleet-ca C:\secure\fleet-ca.crt `
  --fleet-id fleet-large-scale-windows `
  --token-file C:\secure\windows-enrollment-tokens.json
```

Tokens are consumed by the production `neta-agent fleet enroll` command inside the endpoint container. The lab does not synthesize AgentIds or certificates.

## Scenario execution

Run the existing Windows implementation of a NETA-LAB scenario in exactly one endpoint:

```powershell
.\automation\neta-fleet-windows.ps1 scenario `
  --slot win-0002 `
  --scenario 006
```

`NETA-LAB-006` creates the controlled renamed-system-binary process tree and is useful for proving process evidence isolation.

`NETA-LAB-001` is auto-wired to a controlled HTTP peer on the Windows container NAT gateway:

```powershell
.\automation\neta-fleet-windows.ps1 scenario `
  --slot win-0003 `
  --scenario 001 `
  --parameters '{"count":6,"interval_seconds":1}'
```

Other existing Windows scenarios can be launched by passing their native PowerShell arguments in `parameters.args`.

## Persona scheduling

Windows personas live only under `fleet/windows/personas/`, so adding them does not change Linux Phase-2 persona assignment. Scheduling is seeded and repeatable. Most endpoints remain quiet most of the time; threat-like scenarios are deliberately sparse.

```powershell
.\automation\neta-fleet-windows.ps1 schedule --duration 3600
```

## Acceptance

Phase 3 starts with ten endpoints, exactly as required by the roadmap:

```powershell
.\automation\neta-fleet-windows.ps1 `
  --agent ..\neta-agent\build-windows\Release\neta-agent.exe `
  --allow-unenrolled `
  acceptance
```

The acceptance run requires:

1. ten unique container identities;
2. ten unique host root PIDs;
3. ten unique HNS/NAT IP addresses;
4. unique AgentIds when enrollment is enabled;
5. `NETA-LAB-006` process evidence only in `win-0002`;
6. `NETA-LAB-001` connection evidence only in `win-0003`;
7. no process-finding cross-contamination into the other nine endpoint databases;
8. a live broker after both scenarios.

The report is written to `acceptance-phase3.json`. Process evidence is mandatory for the controlled process endpoint. A process finding is produced only when the active production rules/capabilities warrant one; the acceptance test never manufactures or inserts a finding.

## Scale progression

After the ten-endpoint acceptance is green, run the same architecture at:

```text
10
50
100
250
500
```

At every level measure:

- Windows host CPU/RAM;
- container count and process count;
- ETW/broker event rate;
- broker queue drops and unroutable count;
- endpoint database growth;
- coordinator ingestion/heartbeat load;
- scenario completion rate;
- evidence separation.

A scale gate fails if evidence leaks across endpoints, the broker drops materially under normal load, or Windows/HNS resources become unstable.

## Memory-detection compatibility

The process-tree ownership model is intentionally reusable by future process-memory collectors. A privileged host memory sensor can resolve a target PID to its endpoint slot before emitting process-memory evidence. User-space process memory can therefore remain endpoint-scoped. Kernel-memory findings remain host-scoped because process-isolated containers share the Windows kernel; NETA must not present those as 500 independent kernels.
